# Hosted Qwen decision endpoint foundation

## Text conversation endpoint — code ready, not deployed

The Worker now provides a **separate** `POST /chat` endpoint for ordinary, multi-turn study conversations through the native hosted `@cf/qwen/qwen3-30b-a3b-fp8` Workers AI binding. It is **not** a new on-phone Qwen model and does not modify the existing `/assistant` action decision route or automatically edit MYELIN data.

`/chat` accepts only `{ "version":1,"requestId":"unique-id","messages":[{"role":"user","content":"..."}] }` with strict alternating user/assistant text roles, a bounded recent conversation and a final user message. It returns `{ "version":1,"reply":"..." }` only after a **verified Firebase account**, the **same atomic D1 user/shared quotas** and a successful provider reply. It rejects injected system/tool roles, oversized payloads, invalid/partial model outputs, leaked thought tokens, unauthenticated requests and late cancelled generations. No prompt or reply is intentionally persisted by the Worker; the upstream provider processes the user-submitted text.

The app transport in `src/features/assistant/cloud-conversation.ts` and UI in `app/(app)/settings/ai-assistant.tsx` are built to use this route, but remain disabled by default. After an eligible owner has provisioned a **free**, properly authorised Cloudflare Worker, D1 and Firebase token verifier, verified the exact model is available, passed an authenticated **real-inference smoke test**, and approved the provider's student-data terms, configure the public `EXPO_PUBLIC_MYELIN_CHAT_ENDPOINT` URL ending `/chat` in the EAS `preview` environment and publish another OTA. Never set a provider API key in that public variable and never claim the model is working merely because synthetic tests passed. The UI requires an explicit per-session consent switch and verified sign-in; local app actions always retain user confirmation. A general chat request sends only the user message and bounded prior chat turns, not the full workspace.

Backend automated test: `node --test workers/assistant/test/conversation.test.mjs`. App transport and UI test: `npx tsx scripts/verify-cloud-conversation.ts`. Deployment account and Cloudflare Workers AI/D1 bindings are **not connected in this session**, so genuine token/provider smoke testing is still outstanding.


`index.mjs` is a Web API module Worker. Its default entry now constructs real Firebase REST verification and atomic D1 quotas from server bindings; missing/invalid configuration fails closed. It has no Node imports, Admin private key, Gemini call, deployment configuration, billing upgrade or gateway-credit route. `createHandler` accepts trusted server dependencies for verification tests. HTTP bodies/environment activation flags cannot inject authentication or quotas. Binding AI alone returns 503 and consumes no inference. Nothing is deployed and app cloud remains disabled.

Run `node --test workers/assistant/test/*.test.mjs` on Node 22.13+ (Node's SQLite test API is experimental). Tests execute production SQL against actual SQLite, including 12 independent connections/threads contending for shared limits, duplicate requests and the last daily slots. Google account responses and AI remain simulated. This is not workerd CPU, actual D1 consistency, live Firebase revocation or model quality evidence. Production modules import no Node APIs. Canonical instructions/schema are imported directly from `functions/protocol-v1.json`; the existing export parity check remains authoritative.

Prepared transport: POST `/assistant`, `{version:1,prompt:string}`, Firebase bearer token, no-store/release headers and the existing client response envelope. The fixed candidate is `@cf/qwen/qwen3-30b-a3b-fp8`; server requests nonstreaming JSON with 1,200 output tokens and temperature 0.1. Qwen's documented chat-completion envelope must contain exactly one completed assistant choice. Unsupported JSON mode, thinking-only/truncated output, refusal, malformed JSON or wrong request ID fail closed without another generation. The model page advertises `response_format`, but the generic JSON-mode supported list does not list this candidate; actual availability must be verified live rather than assumed. No undocumented thinking API parameter is used.

Provider decisions still need the app's full Mini field/reference/grounding validation and explicit preview confirmation. Server envelope validation is not a semantic accuracy guarantee. Inputs exceeding a conservative 30,000 combined system/schema/prompt UTF-8 bytes are rejected, not truncated, to leave headroom in the documented 32,768-token context. This is a conservative byte bound, not measured tokenizer usage or free-capacity certification.

All HTTP phases share a maximum 25-second response deadline, including streaming body reads, auth, quota reservation, AI and lease cleanup. A reservation is allowed to settle after the HTTP timeout so its lease can be released; production quotas must have crash-safe expiration. The binding may continue GPU work after cancellation: the adapter discards the result and never retries. Attempts must remain charged. Provider codes 3036 (daily Free exhaustion), 3040 (capacity) and 5035 (paid-plan requirement) are sanitized; exhaustion waits until the next UTC reset and never asks the server to upgrade. Actual binding error shapes remain a live-verification requirement.

## Authentication and quota bindings

Required server configuration: `AI`, `ASSISTANT_DB` (D1), `FIREBASE_PROJECT_ID`, `FIREBASE_WEB_API_KEY`. Apply `migrations/0001_quotas.sql` once through D1 migrations before running. `MYELIN_RELEASE_COMMIT` is optional public evidence. The Firebase Web API key identifies the existing project; it is not an Admin credential. No secrets or identity dependencies can be provided by HTTP callers. Deployment configuration is intentionally deferred to the next runtime-verification chunk.

Each call sends the complete Firebase ID token to the fixed HTTPS Google `accounts:lookup` API with redirects disabled. Google authenticates the signed token; local JWT decoding only checks the expected project, issuer, UID, timestamps and unsupported tenant before the mandatory successful remote verification. No decoded-only acceptance or successful identity caching. The returned UID must match; original `auth_time` must be at least server `validSince`, even if the token was refreshed later. Disabled/deleted/invalid tokens reject. Missing or malformed revocation metadata, Google/API-key errors and unavailable services reject without generation. Both current account and token must agree on verified email; anonymous users reject. Authentication fetch/body has a five-second deadline and response byte bound within the endpoint's total deadline. Live tests must prove this project's key permits lookup and supplies revocation metadata, then check a real revoked/disabled account. Missing metadata will block rather than silently drop the check.

D1 authorization uses one transactional `batch`: retention cleanup, conditional attempt/lease insert, diagnostic read. All user/shared predicates are inside the write statement, never a separate read granting a later write. Database UTC time fixes minute/day boundaries at transaction execution, even after queueing. Defaults: user 2/minute, 8/day; shared 4/minute, 24/day; one active request per user, two shared. These are conservative application caps, not a measured neurons allowance. No runtime/environment cap override or paid fallback. Daily reset is UTC, shared with the provider allowance. A database failure or ambiguous reservation response cannot authorize inference.

Attempts store only hashed UID/request ID, random lease ID and timestamps. Dedupe retention is seven days; denied requests do not consume an attempt. Admitted failures and cancellation do; cleanup clears only the matching lease and never refunds counts. Leases expire after 90 seconds following crashes. Old release callbacks cannot clear a newly admitted lease. Expiry bounds endpoint reservations, not continued provider GPU work after a timeout. Shared provider cooldown only increases; missing control state blocks service. No in-memory quota fallback or automatic provider retry. A dedicated database is required: application caps do not track other account consumers of Workers AI.
